# Trampas conocidas
Para no perder tiempo redescubriéndolas.

- **`src/navigation/AppNavigator.tsx` está muerto.** No compila (importa `@react-navigation/native-stack`, que no está instalado) y no se usa en ningún lado. El navegador raíz real es `App.tsx` (cargado vía `index.ts`), envuelto en `ThemeProvider > AuthProvider > NavigationContainer`. Si `tsc` marca un error ahí, es preexistente y se ignora.
- **Confirmación de correo activada en Supabase:** `signUp` no da sesión inmediata. Por eso `RegisterScreen` guarda `pending_account_type`/`pending_org_name`/`pending_invite_code` en los metadatos del usuario — así `LoginScreen` puede retomar el onboarding (crear o unirse a organización) después de que el usuario confirme su correo y vuelva a entrar.
- **`organization_members` y `profiles` ya permiten ver a todo tu equipo, no solo tu propia fila** (`organization_members_select_org` / `profiles_select_org_members`, vía la función `my_organization_ids()`). Se habilitó para que el Semillero pueda evaluar skills/idiomas/badges de todos los miembros al sugerir equipo. El Dashboard todavía no usa esto para mostrar conteo real de miembros, pero ya podría (antes daba 1 siempre con `organization_members_select_own`).
- **Nunca poner la `secret`/`service_role` key de Supabase en `.env`** (solo la `anon`/`publishable`, que va al cliente). Ya pasó una vez en este proyecto.
- **`AGENTS.md` dice Expo SDK 56, pero lo instalado es SDK 54** (`~54.0.0` en `package.json`/`app.json`). Si hace falta consultar docs versionadas de Expo, usar v54, no v56.
- **Las políticas de Postgres (`create policy`) no son idempotentes** (no existe `if not exists` para políticas). Por eso `schema.sql` hace `drop policy if exists "..." on tabla;` antes de cada `create policy` — así es seguro re-correr el archivo completo cada vez que se le agrega algo, en vez de tener que copiar solo el bloque nuevo. Mismo criterio para constraints que cambian de valores permitidos: `alter table ... drop constraint if exists ...` + `add constraint` en vez de un `DO $$ IF NOT EXISTS $$` (ver `task_comments_attachment_type_check` en `schema.sql`, que pasó de 2 a 4 valores permitidos).
- **`assets/images/avatares/` se ha vaciado solo más de una vez** (parece un problema de sincronización de OneDrive, no de git — la carpeta ni siquiera está trackeada). `src/lib/profiles.ts` hace `require()` estático de cada archivo en `DEFAULT_AVATARS`; si falta uno solo, Metro no arma el bundle y **toda la app queda en blanco** (no solo la pantalla de perfil). Si la app se ve en blanco sin razón aparente, revisar esta carpeta antes que nada.
- **En web, `height: "100vh"` en la pantalla raíz NO es suficiente para acotar un layout con footer fijo (composer/sticky bar).** El wrapper de pantalla interno de `@react-navigation/stack` tiene `min-height: 100%` pero **no** `flex: 1`, así que crece con el contenido en vez de quedar acotado al viewport — un `ScrollView` interno con contenido largo puede empujar todo hacia abajo sin que haya forma de hacer scroll (le pasó a `SemilleroScreen`). La solución que funciona es anclar la pantalla directo al viewport con `position: "fixed", top:0, left:0, right:0, bottom:0` (solo en web; en nativo `flex:1` normal). Ver `rootStyle` en `SemilleroScreen.tsx`.
- **`Alert.alert()` de React Native es un no-op completo en web** (`react-native-web/src/exports/Alert/index.js` literalmente no hace nada — ni diálogo ni callbacks). Nunca usarlo para confirmaciones que deban funcionar en el navegador (ej. "¿borrar esto?"); usar un estado local + UI inline (o modal propio) que funcione igual en los 3 targets. Ver el patrón de confirmación de borrado en `SemilleroScreen.tsx` y `TasksScreen.tsx` (`confirmDeleteId`).
- **Los íconos de equipos/proyectos y los adjuntos de chat de tasks se suben al bucket de Storage `avatars`** (no hay un bucket `icons`/`attachments` separado) bajo la carpeta del usuario que los sube (`${userId}/<prefix>-<timestamp>.<ext>`), porque las políticas de ese bucket ya permiten a cualquier autenticado escribir en su propia carpeta y leer cualquier archivo público — crear un bucket nuevo hubiera sido infraestructura redundante. Ver `uploadFile` en `src/lib/icons.ts`.
- **Un `TextInput` de "pega una URL" necesita confirmar también en `onBlur`, no solo en `onSubmitEditing`/botón.** Sin eso, pegar la URL y hacer clic en otro campo (el gesto más natural) perdía el valor silenciosamente — pasó con el ícono de `IconColorPicker.tsx`, y el mismo patrón se reusó para el input de link en el chat de comentarios de `TasksScreen.tsx`. Cualquier input de "pega esto y sigue" nuevo debería confirmar en los 3 momentos (submit, botón, blur).
- **`App.tsx` decide la pantalla inicial según si ya hay sesión (`RootNavigator`, dentro de `AuthProvider`), no un `initialRouteName="Landing"` fijo.** Antes, recargar la página en web (F5) siempre mandaba a Landing sin importar que hubiera sesión activa, porque nadie redirigía a "Main" al restaurar la sesión. Ahora `RootNavigator` muestra un splash mientras `useAuth().loading` es `true` y luego decide `initialRouteName={session ? 'Main' : 'Landing'}` — si se toca este archivo, no volver a un `Stack.Navigator` con ruta inicial fija sin pasar primero por ese gate.
- **Las pantallas dentro de `BottomTabs` (Dashboard/Projects/Team/Tasks) deben usar `useFocusEffect` de `@react-navigation/native` para cargar datos, no `useEffect` a secas.** Los tabs quedan montados al cambiar de pestaña (no se desmontan), así que un `useEffect(() => fetch(), [organization])` solo corre una vez al montar — crear un proyecto y volver al home no reflejaba nada hasta recargar toda la página. `useFocusEffect(useCallback(() => fetch(), [...]))` sí se dispara cada vez que la pantalla vuelve a tener foco.
- **Las sugerencias del Semillero (`team_suggestion`) pueden quedar obsoletas** si los usuarios que sugirió la IA cambiaron de organización o se borraron después de generarse (p. ej. limpieza de `seed_users.sql`). Insertar directo revienta con un error de foreign key críptico (`projects_leader_id_fkey` / `teams_leader_id_fkey`). Por eso `SemilleroScreen.tsx` valida con `findMissingSuggestionMembers` (compara contra `listOrganizationMembers` actual) ANTES de llamar a `createProjectFromSuggestion`/`createTeamFromSuggestion`, y muestra los nombres exactos que ya no pertenecen en vez de dejar pasar el error de Postgres.
- **"Ver proyecto"/"Ver equipo" (evitar re-crear al reintentar) se guarda en la BD, no en estado local.** `team_suggestion.createdProjectId`/`createdTeamId` (ver `TeamSuggestion` en `lib/semillero.ts`) se actualiza vía `updateMessageTeamSuggestion` justo después de crear con éxito. Antes esto vivía solo en un `useState` del componente — al navegar a Proyectos/Equipos tras crear y volver al Semillero, `SemilleroScreen` se remonta, ese estado se perdía, y un segundo clic en el mismo botón intentaba crear todo de nuevo (y a veces fallaba). Requiere la policy `semillero_messages_update_own` (RLS) para poder hacer ese `update`.
- **En `tasks`, la RLS policy de `update` deja pasar la fila tanto al líder/owner como al asignado — la restricción de QUÉ columnas puede tocar cada quién no vive en la policy, vive en un trigger.** `enforce_task_update_permissions` (BEFORE UPDATE) compara `old` vs `new` y rechaza el update si alguien sin privilegio intenta cambiar algo que no sea `status`. Si se agrega una columna nueva a `tasks` (ej. fecha límite, prioridad), hay que sumarla explícitamente a esa comparación en el trigger — de lo contrario cualquier asignado podría editarla sin que la RLS lo detecte (la policy de `update` no distingue columnas, solo filas).
- **Un `PanResponder` creado con `useRef` (para que no se recree en cada render) captura los props/valores del momento en que se creó — si esos valores cambian después (ej. las fechas de una task tras guardarse), los callbacks del gesto siguen viendo los viejos.** Pasa en `TaskGanttChart.tsx`: cada barra arrastrable tiene su propio `PanResponder` (uno para mover, uno por cada handle de resize) creado una sola vez vía `useRef(...).current`. La solución es un ref "latest" separado (`useRef({ effectiveStart, effectiveEnd, ... }); latest.current = {...}` reasignado en cada render, plain assignment, sin `useEffect`) que los callbacks del PanResponder leen en el momento del gesto (`onPanResponderRelease`) en vez de cerrar sobre las variables directamente. Mismo patrón a reusar en cualquier gesto complejo nuevo que dependa de datos que puedan refrescarse desde el servidor mientras el componente sigue montado.
- **En nativo (iOS/Android/Expo Go), `useWindowDimensions()` no sirve de nada si `app.json` tiene `"orientation": "portrait"` fijo** — la app ni se entera de que el teléfono giró, porque el sistema operativo la bloquea en portrait antes de que React Native reciba el evento de resize. Rotar el emulador para ver el Gantt con más espacio horizontal (o cualquier pantalla) simplemente no hacía nada por esto, no por un bug de layout. Cambiado a `"orientation": "default"` (permite cualquier orientación, gobernada por el sensor/rotación del dispositivo) — requiere recargar la app completa en Expo Go (no alcanza con el fast refresh de Metro) para que tome el `app.json` nuevo. Web no se ve afectado por este flag (no hay bloqueo de orientación en browser).
- **`npx tsc --noEmit` puede reventar con `RangeError: Maximum call stack size exceeded` en este entorno (Node 22 + la versión de TypeScript instalada), sin relación con ningún cambio de código** — se confirmó corriéndolo sobre el `HEAD` limpio (sin cambios) y falla igual. Si hace falta validar tipos, usar `node --stack-size=8000 ./node_modules/typescript/bin/tsc --noEmit` para esquivarlo; con eso el único error que queda es el ya documentado de `AppNavigator.tsx` (archivo muerto, ver arriba).
- **Un link de "ver más" que solo se renderiza dentro de la rama "hay datos" deja a la organización sin forma de llegar a esa pantalla mientras el dato esté vacío.** Pasó con la tarjeta "Actividad reciente" del Dashboard: el link "Ver toda la actividad" que navega a `ActivityScreen` solo existía dentro del `else` de `recentActivity.length === 0 ? (...) : (...)`, así que una organización que recién empezaba a usar el feature (cero actividad todavía) no tenía NINGUNA forma de llegar a esa pantalla — ni tile, ni tab, nada. La regla general: si un empty-state es la única puerta de entrada a una pantalla completa (no solo un placeholder decorativo), ese empty-state necesita su propio link/botón de navegación, no asumir que "cuando haya datos, aparecerá el link".
- **Antes de asumir que un feature nuevo tiene un bug de backend, confirmar que la tabla/policy realmente se corrió** con una query REST directa usando la `anon` key (sin sesión) contra `<SUPABASE_URL>/rest/v1/<tabla>?select=id&limit=1`: un `404` con `PGRST205` ("Could not find the table...") significa que la tabla no existe (falta correr `schema.sql`); un `200` con `[]` solo significa que RLS filtró todo (normal sin sesión) o que la tabla existe pero está vacía — no descarta ni confirma que haya filas reales para la organización del usuario. Sirvió para descartar rápido "no corriste el schema" como causa del bug real de navegación de arriba.
- **Reusar `primaryColor` para "lo que sea que necesite un color de acento" filtra el color de marca del workspace a elementos que no deberían tenerlo.** Pasó al aplicar el sistema de vidrio azure (ver `docs/PATRONES.md`) en paralelo con varios agentes: `ProjectsScreen.tsx`, `TeamScreen.tsx` y `SemilleroScreen.tsx` quedaron con `const primaryColor = organization?.color ?? AZURE_DEEP` (en vez del azure fijo que usa el resto de la app) porque esa era la forma en que esas pantallas ya calculaban su acento *antes* del rediseño, y nadie la separó al agregar las manchas de fondo (`blobStyle(primaryColor, ...)`). Resultado real: si el owner de la organización de prueba eligió un color magenta/rosado para su workspace en `WorkspaceSetupScreen`, la mancha de fondo (pensada para ser azure, decorativa, de marca de *Nexus*) salía magenta — un bug puramente visual pero confuso, porque no hay ningún hex "magenta" hardcodeado en ningún lado del código; el color viaja dinámicamente desde `organizations.color` en la base de datos. La lección: `primaryColor` (acento fijo de Nexus) y `orgColor`/`organization.color` (marca elegida por cada workspace) tienen que ser dos variables con nombre distinto siempre, nunca una con fallback a la otra — ver el bullet de `primaryColor` vs `orgColor` en `docs/PATRONES.md`. Si algo se ve "mal coloreado" sin que haya un hex sospechoso en el archivo que estás mirando, sospechar de una variable dinámica (`organization.color`, `avatar_color`, `team.color`, `project.color`) que se coló donde no correspondía.
- **Un agente delegado con un alcance acotado ("solo limpieza de código muerto, cero cambios de lógica") puede igual devolver cambios de lógica no pedidos, y decirlo explícitamente en su propio resumen final sin que eso lo vuelva autorizado.** Pasó de verdad limpiando el código muerto que quedó tras remover las manchas de fondo (`blobStyle`) del rediseño "vidrio azure": el agente reportó honestamente "tarea nueva que llegó mientras trabajaba" y reescribió la tarjeta de "Proyectos" del `DashboardScreen.tsx` (de un conteo simple a una grilla de mini-tarjetas con datos reales, +155/-87 líneas) — nadie pidió eso, ni el usuario ni la instrucción que se le dio al agente. Se detectó revisando `git diff --stat` de cada archivo que el agente tocó (un diff mucho más grande de lo que "borrar una función y una constante" debería producir) antes de confiar en el resumen, y se revirtió esa parte puntual manteniendo la limpieza real que sí se había pedido. La lección: "trust but verify" aplica también cuando el propio agente admite que hizo algo fuera de la consigna — la honestidad del resumen no reemplaza la revisión del diff real antes de darlo por bueno.
- **Para una grilla tipo Gantt (columna de labels fija + área de contenido con scroll horizontal, ambas con scroll vertical sincronizado), no hace falta sincronizar manualmente dos `ScrollView`.** El truco en `TaskGanttChart.tsx`: UN solo `ScrollView` vertical envuelve una fila (`flexDirection: "row"`) con la columna de labels (View normal, sin scroll propio) al lado de un `ScrollView horizontal` que contiene la grilla de días — como labels y grilla están dentro del MISMO `ScrollView` vertical exterior, se desplazan juntos verticalmente sin código extra; el horizontal solo afecta a la grilla porque el label column vive fuera de ese `ScrollView` interno. En web esto es gratis (son `overflow` de CSS anidados); en nativo, anidar scrolls de direcciones DISTINTAS (vertical fuera, horizontal dentro) no genera conflicto de gestos — el problema clásico es anidar la MISMA dirección.
- **`denomailer` (cliente SMTP nativo de Deno) falla con `Error: invalid cmd` contra Gmail dentro del runtime de Edge Functions de Supabase, sin importar el puerto.** Se probó primero para los correos transaccionales (`docs/EMAILS.md`) porque es la opción "nativa" de Deno — pero tiró el mismo error tanto en 587 (STARTTLS) como en 465 (TLS directo), lo que descarta que fuera un problema de configuración: es una incompatibilidad de esa librería (años sin mantenimiento) con la versión de Deno del runtime de Supabase (`supabase-edge-runtime`). La solución fue reemplazarla por `nodemailer` (import `npm:nodemailer@6.9.16`, igual que ya se hace con `npm:@supabase/supabase-js`) — mucho más madura/probada, funcionó al primer intento con las mismas credenciales. Si algo nuevo necesita hablar SMTP crudo desde una Edge Function, preferir `nodemailer` (u otro paquete `npm:` maduro) antes que una librería Deno-nativa de este estilo.
- **Gmail (y varios otros clientes de correo) bloquean/no renderizan `<img src="data:image/png;base64,...">` embebido en el cuerpo de un email** — el logo de Nexus en el header de las plantillas de `docs/EMAILS.md` se armó primero así (evitando depender de una URL pública) y salía roto en la bandeja real. La forma que sí funciona de forma consistente es un **adjunto embebido vía `cid`**: con `nodemailer`, pasar `attachments: [{ filename, content: base64String, encoding: "base64", cid: "un-id" }]` en `sendMail()` y referenciar `<img src="cid:un-id">` en el HTML (ver `supabase/functions/_shared/smtp.ts` + `_shared/email_templates.ts`). El logo/nombre de LA ORGANIZACIÓN (`organizations.logo_url`), en cambio, sí es una URL real (subida a Storage) y se puede usar directo como `<img src="https://...">` sin este problema — la trampa es específica de `data:` URIs, no de imágenes en general dentro de un correo.
- **Un badge/ribbon flotante (`position: "absolute", top: -N`) sobre una card con `borderRadius` grande puede solaparse con el propio borde redondeado y "comerse" un pedazo visual del contorno.** Pasó en las cards de precio de `PricingSection.tsx` (Landing): el pill "Más popular" se posicionaba a caballo del borde superior de la card (mitad afuera, mitad adentro), y como el pill es un rectángulo con esquinas propias sentado justo sobre la curva del `borderRadius` de la card, la intersección se veía como si le faltara un pedazo al borde en vez de flotar limpio arriba. La solución fue sacar el badge del posicionamiento absoluto: ahora es un elemento normal en el flujo, en una fila propia (`badgeRow`, altura fija) ANTES de la card — la card no destacada lleva la misma `badgeRow` vacía como espaciador para que ambas arranquen a la misma altura en desktop (lado a lado). Ese espaciador invisible solo tiene sentido cuando las cards están lado a lado — en mobile (columna apilada) hay que sacarlo (`!isMobile &&`), si no deja un hueco vacío feo entre una card y la siguiente sin ningún propósito visual.
- **Una columna angosta con texto en negrita puede partir una palabra larga a la mitad en vez de bajarla entera a la siguiente línea, si ni la palabra sola entra en el ancho disponible a ese tamaño de fuente.** Pasó en la tabla comparativa "Otras plataformas vs. Nexus" de `PricingSection.tsx`: en mobile, "Cumplimiento normativo" se renderizaba como "Cumplimien" / "to" / "normativo" (3 líneas, con la palabra partida) porque ni "Cumplimiento" (12 caracteres, bold) entraba en el ancho de columna que le tocaba a ese `fontSize`. No es un bug de `flexWrap`/word-break explícito en el código — es el comportamiento por defecto de `Text` cuando una palabra individual excede el contenedor. La solución fue bajar `fontSize` y ajustar `flex`/`paddingHorizontal` de las 3 columnas específicamente bajo `isMobile` (no reusar los mismos valores que desktop) — con más aire disponible, la palabra completa vuelve a entrar en una sola línea. Si se agrega contenido con palabras largas dentro de una columna angosta nueva, probar el layout real en mobile (390px) antes de asumir que el `flexWrap` por defecto se ve bien a cualquier ancho.
- **Un `flex: N` pensado para dividir el ANCHO entre hermanos en fila se convierte en una división del ALTO si ese mismo contenedor pasa a columna en mobile (`flexDirection: isMobile ? "column" : "row"`) — y como el ratio entre hermanos no suele coincidir con el ratio real de sus alturas de contenido, uno de los dos termina con un hueco vacío o el otro comprimido.** Pasó en `DashboardMockup.tsx`: `tasksCard` (`flex: 3`) y `reportCard` (`flex: 2`) dividían bien el ancho en fila (desktop), pero al apilarse en columna (mobile) ese mismo 3:2 se aplicaba al alto — como el contenido real de `tasksCard` no pesa 1.5x el de `reportCard`, quedaba con un hueco vacío grande al final. La regla general: cualquier `flex` puesto pensando en un layout de fila necesita revisarse (o anularse) explícitamente para el layout de columna correspondiente en mobile — no asumir que un ratio pensado para ancho sigue teniendo sentido aplicado a alto.
- **Para anular un `flex`/estilo heredado de un array de estilos condicionalmente (`[stylesBase, isMobile && { ... }]`), pasar `{ flex: undefined }` NO funciona en React Native Web** — el merge de estilos ignora las claves con valor `undefined` en vez de usarlas para "borrar" el valor que venía del objeto anterior del array, así que el `flex: 3`/`flex: 2` original seguía activo (confirmado con `getComputedStyle`: `flexGrow` seguía en `3` después de aplicar `{ flex: undefined }`). Peor todavía: `{ flex: 0 }` tampoco es un reemplazo seguro — el shorthand `flex: 0` fija `flexBasis: "0%"` (no `"auto"`), lo que colapsa el tamaño inicial del elemento a cero y puede hacer que su contenido se superponga con el hermano siguiente en vez de reservarle espacio. La forma que sí funciona es pisar explícitamente las 3 longhand: `{ flexGrow: 0, flexShrink: 0, flexBasis: "auto" }` — eso sí fuerza que el elemento mida su contenido real, sin arrastrar el `flexBasis: 0%` del shorthand. Ver `DashboardMockup.tsx`.
