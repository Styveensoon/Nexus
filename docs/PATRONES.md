# Patrones de código ya establecidos
Reusar, no reinventar.

- **Paleta local por pantalla** (no hay theme file compartido para las pantallas nuevas): cada componente calcula sus propios `bg`, `cardBg`, `border`, `textPrimary`, `textSecondary`, `primaryColor = "#2563EB"` (u `organization?.color` cuando aplica), `inputBg` a partir de `isDark` (de `useTheme()`). Copiar el bloque tal cual de cualquier pantalla ya rediseñada en vez de crear una paleta nueva.
- **Sombra:** patrón `ultraShadow` vía `Platform.select({ web: { boxShadow, backdropFilter: "blur(12px)" }, default: { shadowColor/Offset/Opacity/Radius, elevation } })`.
- **Responsive:** `const isMobile = useWindowDimensions().width < 768` en cada pantalla — no hay breakpoints centralizados. Contenido en desktop va dentro de un contenedor `maxWidth` centrado (960–1280 según la pantalla).
- **Íconos:** `lucide-react-native` en todo el proyecto — ya no queda ninguna pantalla usando `@expo/vector-icons` (la última, la vieja `CalendarScreen`, se eliminó al fusionarse como vista dentro de Tasks).
- **Ícono + color personalizado de una entidad (equipo/proyecto):** `IconColorPicker.tsx` tiene dos secciones rotuladas ("Imagen" / "Color"), no una sola fila apretada. "Imagen": preview y `AvatarUploadZone` (drag-and-drop en web / picker nativo) del mismo tamaño (`AVATAR_TILE_SIZE`, 84px) lado a lado, con el input de URL pegada ocupando el ancho completo debajo (confirma con Enter, el botón de flecha, **o al perder el foco** — pegar y hacer clic afuera debe aplicar igual). Sube a través de `uploadIconFile` en `src/lib/icons.ts` (reusa el bucket `avatars`, ver `docs/TRAMPAS.md`). Si no hay ícono, se cae a un ícono de lucide (`fallbackIcon`) coloreado con el color elegido. "Color": 5 muestras rápidas (`PRESET_COLORS`) + un círculo punteado para personalizar (`ColorPickerModal`), con el hex mostrado debajo — no un solo swatch-pill con chevron.
- **Mostrar los badges de alguien (`BadgePill.tsx` + `BadgeDetailModal.tsx`):** `BadgePill` es un pill minimalista (ícono de lucide + nombre, coloreado con el color del badge, dos tamaños `sm`/`md`) — mismo lenguaje visual que los chips de habilidades/idiomas. Es el único lugar que mapea el nombre de ícono (string, `BadgeDefinition.icon`) a un componente real de lucide (`BADGE_ICONS`, exportado para que otros componentes lo reusen en vez de duplicar el mapa). Acepta un `onPress` opcional — pasarlo abre `BadgeDetailModal` (mini modal con "Otorgado por X · fecha", usa `ProfileBadge.grantedByName` que ya viene resuelto desde `lib/badges.ts`, sin necesidad de cargar el roster de la organización). Se usa así en `ProfileScreen` (los propios badges), `MemberProfileModal` (los de quien se está viendo — el perfil de solo lectura que abre `TeamScreen` al elegir integrantes) y `BadgesScreen`/`BadgeAwardModal`. Si una pantalla nueva muestra badges de alguien, reusar `BadgePill`+`BadgeDetailModal` (con `onPress`) en vez de reinventar el chip o la tarjeta de detalle.
- **Elegir integrantes de la organización (picker con buscador):** en vez de una lista de chips, `TeamScreen` muestra el roster disponible como tarjetas (avatar + nombre + rol) con un buscador arriba; tocar una tarjeta abre `MemberProfileModal.tsx` (perfil de solo lectura reusando la misma info que `ProfileScreen`: bio, zona horaria, habilidades, idiomas) con un botón de acción contextual ("Agregar al equipo" / "Quitar del equipo"). Mismo componente sirve para ver el perfil de alguien ya agregado, tocando su card en la lista de integrantes del borrador.
- **Botones primarios:** píldora (`borderRadius: 999`).
- **Filosofía anti-fake:** nunca simular que algo funciona cuando no hay backend. Si no hay feature real, se muestra un estado vacío honesto o un aviso tipo "esto estará disponible pronto" — nunca un spinner falso ni un botón que aparenta éxito. (Ver las secciones Badges/Equipos de `ProfileScreen.tsx`, o `ProjectsScreen.tsx`, que muestra un banner de error honesto en vez de ocultar un fallo de red.)
- **Formularios reusables:** la edición de perfil vive en `src/components/ProfileEditorForm.tsx` (self-contained: hace su propio fetch/save) y la usan tanto `ProfileSetupScreen` (onboarding, sin botón cancelar) como `ProfileScreen` en modo edición (con cancelar) — pasarle `onCancel` o no cambia el layout del botón de guardar.
- **Modales tipo picker:** `ColorPickerModal` (hue bar + hex), `TimezoneModal` (búsqueda + lista, selección única, se autocierra al elegir), `LanguageModal` (igual que `TimezoneModal` pero multi-selección: tocar una fila la agrega/quita del arreglo en vez de cerrar el modal), `TaskStatusPickerModal` (lista corta sin buscador — punto de color + label + check en el actual, para status de tasks) y `DatePickerModal` (calendario mes a mes, usado en el chat de comentarios de Tasks) comparten el mismo overlay/card (`overlay`/`card`/`header` con título + X). El botón que abre cualquiera de estos sigue el mismo `selectorBtn` (ícono + texto + `ChevronDown`, ver `ProfileEditorForm.tsx`). Para inputs "arrastrables" (slider discreto), ver `LevelDots.tsx` (usa `PanResponder`, igual que la hue bar del color picker; acepta `disabled` para modo solo-lectura).
- **Abanico de opciones comunes + personalizado (chips toggle + texto libre):** cuando un campo tiene algunas opciones típicas pero no es una lista cerrada (`TEAM_ROLE_OPTIONS` en `src/lib/teams.ts`, `PROJECT_AREA_OPTIONS` en `src/lib/projects.ts`), se muestra un abanico de chips que funcionan como toggle (tocar agrega/quita, comparación case-insensitive) **más** un input de texto libre para cualquier valor que no esté en la lista — nunca uno solo de los dos. Si el estado ya elegido se muestra en una lista de chips removibles aparte (como en "Áreas involucradas" de `ProjectsScreen.tsx`), esa lista debe filtrar las opciones que ya vinieron del abanico (que ya muestran su propio estado seleccionado) para no duplicarlas — solo mostrar ahí lo que sí es personalizado.
- **Reemplazar "ciclar" por selección directa cuando las opciones crecen:** tocar un badge de estado para ir avanzando una por una (`nextStatus`/`handleCycleStatus`) es aceptable con pocos valores (ver `ProjectStatus`, 4 valores, en `ProjectsScreen.tsx`), pero deja de servir cuando son muchos — `TaskStatus` pasó de 4 a 8 valores y el badge de status del Kanban en `TasksScreen.tsx` pasó de ciclar a abrir `TaskStatusPickerModal` (selección directa). Si se agrega un estado nuevo a algo que hoy cicla, reconsiderar si sigue siendo la UX correcta en vez de agregarlo sin más al ciclo.
- **Renglón de actividad (`ActivityRow.tsx`):** ícono (mapeado desde el `action` de un `ActivityEntry`, `src/lib/activity.ts`) + texto "quién hizo qué" (`describeActivity()`) + fecha y hora completas. Reusado tal cual en la tarjeta "Actividad reciente" del Dashboard y en los 4 apartados de `ActivityScreen.tsx` — si se necesita mostrar actividad en una pantalla nueva, reusar este componente en vez de armar la fila a mano.
- **Código específico de plataforma:** cuando algo necesita DOM real en web (ej. `AvatarUploadZone` con drag-and-drop, `ChatAttachmentButtons` con `expo-image-picker`/`expo-document-picker`), usar el patrón `Componente.tsx` (nativo) + `Componente.web.tsx` (web) — Metro resuelve el archivo correcto por plataforma solo con el nombre.
- **Subida de archivos genérica:** `uploadFile(ownerUserId, data, contentType, ext, prefix)` en `src/lib/icons.ts` es la función base (bucket `avatars`, carpeta por usuario) — `uploadIconFile` (íconos de equipo/proyecto) y `uploadTaskAttachment` (adjuntos de chat de tasks, en `src/lib/tasks.ts`) son wrappers delgados sobre ella con un `prefix` distinto para que el nombre del archivo en Storage sea legible.
- **Vistas intercambiables sobre los mismos datos (switch Kanban/Lista/Calendario/Gantt en `TasksScreen.tsx`):** cada vista es un componente self-contained en `src/components/` (`TaskListView.tsx`, `TaskCalendarView.tsx`, `TaskGanttChart.tsx`) que recibe `tasks`/`projects` ya cargados por props — **no hacen su propio fetch** (a diferencia de `ProfileEditorForm.tsx`, que sí es self-contained con fetch propio porque vive en más de un flujo). El padre (`TasksScreen`) es la única fuente de verdad de los datos; cambiar de vista solo cambia cómo se renderiza, nunca dispara una carga nueva. Si se agrega una vista nueva, seguir este patrón en vez de que cada vista cargue sus propios datos.
- **Modales de formulario en desktop no van en una sola columna angosta.** `modalCardWide` (1080px, en vez del `modalCard` base de 460px) + un layout de dos columnas: `formLayout` (`flexDirection: "row"`) con `formMain` (flex 1.5) y `formSide` (300px fijo). Solo aplica con `!isMobile &&`; en mobile todo se apila en una columna igual que antes. Qué contenido va en cada columna **no es fijo, depende de cuál sección es más pesada/rica en ese formulario específico**: en `TasksScreen.tsx` (crear/editar/ver task) y `ProjectsScreen.tsx` (crear/editar proyecto) el texto (título/descripción/asignación o nombre/descripción/ícono) va en `formMain` y la metadata compacta (prioridad/fechas/adjuntos, o metas/áreas/equipos) en `formSide`; en `TeamScreen.tsx` (crear/editar equipo) es al revés — Integrantes (buscador + roster scrollable + tarjetas de rol) es lo pesado y va en `formMain`, mientras Nombre/Descripción/Ícono (compactos) van en `formSide`. Decidir según el formulario, no copiar la asignación de columna literal de otra pantalla. Si se abre un modal de formulario nuevo en otra pantalla, reusar `modalCardWide`/`formLayout`/`formMain`/`formSide` en vez de dejarlo angosto dentro de un modal ancho.
